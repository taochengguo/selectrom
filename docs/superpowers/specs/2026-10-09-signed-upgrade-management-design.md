# 签名软件包升级管理设计

## 目的与部署前提

管理员希望在随机抽样系统电脑端后台查看当前版本、上传由项目发布流程生成的软件包，并发起升级。首个目标环境是天翼云 Ubuntu 24.04（2 核、2 GB 内存）的 Nginx + Gunicorn + Django + MySQL 部署。Windows 本机演示路径仍由现有脚本维护；升级功能在没有安装独立更新服务时显示“当前环境未启用软件包升级”，不得假装升级成功。

升级会替换可执行代码和执行数据库迁移，属于系统维护权限。现有 `role=admin` 仅代表业务管理员；升级入口与操作需要 `is_superuser` 且 `is_active`，并要求输入当前密码再次确认。普通业务管理员和抽样员无法查看升级包内容、上传包或发起升级。关键操作记录操作者、时间、源 IP、包版本、包摘要和结果；记录不包含私钥、数据库密码或完整环境变量。

## 方案边界

1. **发布端：** 在受控的 Linux 发布环境从指定 Git 提交构建包。包内包含应用文件、Linux 运行依赖的离线 wheelhouse、版本号、目标平台、最低可升级版本、文件摘要清单和迁移信息。发布流程用 Ed25519 私钥对规范化清单签名，私钥不进入仓库或服务器。服务器只配置可信公钥；公钥轮换需单独的运维步骤。
2. **后台：** “升级管理”页面展示当前版本、已上传包及状态、最近升级记录。上传时以流式方式写入专用暂存目录，对压缩包大小、解压后总量、路径穿越、绝对路径、符号链接、重复成员和意外文件进行拒绝校验；验证完整摘要、签名、目标平台及版本兼容性后才可进入“待确认”。任何失败都不触碰当前程序。
3. **确认：** 系统维护账号查看版本、来源提交、迁移提示和备份空间估算，再输入密码确认。一次只允许一个升级作业。Web 进程只提交作业，不具备写入当前发布目录、控制 systemd 或执行 shell 的权限；上传包不作为脚本直接运行。
4. **执行端：** 独立 systemd 更新服务从受保护作业队列获取已确认的包，重新验证签名与摘要，并将包展开到新的只读 release 目录。更新服务先确认磁盘空间，进入维护状态、停止应用写入，备份 MySQL 与 `media/`、`SamplingPhotos/`，在新 release 的隔离虚拟环境安装离线依赖，执行 `manage.py check`、迁移和静态文件收集，原子切换 `current` 链接，重启并探测健康端点。状态与详细日志持久化在独立于应用数据库的受保护目录，以便数据库暂时不可用时仍能诊断。
5. **恢复：** 在迁移开始前失败时，保持旧 release 运行并清理未启用的新 release。迁移开始后失败时，停止应用、恢复此次完整数据库及上传文件备份、切回旧 release，再重启并验证；若自动恢复也失败，维持维护状态并显示人工恢复命令和备份位置。升级成功前不删除旧 release 或此次备份；保留数量及空间策略由部署文档明确。

## 状态与接口

包状态：`uploaded` → `validated` / `rejected` → `queued` → `running` → `succeeded` / `failed` / `recovery_required`。状态变更必须可审计且不可由浏览器任意指定。页面通过只读状态接口轮询，不向浏览器返回服务器绝对路径、命令行或敏感日志。上传、确认和取消等待中的作业均为 CSRF 保护的 POST；运行中的升级不可由 Web 页面强制中断。

当前版本来自 release 元数据，而不是可由数据库任意编辑的显示字段。每个包绑定确切 Git 提交；相同版本、低版本、平台不匹配、签名失败或目录容量不足时不能确认执行。升级开始前阻止新的升级确认；执行期间向用户显示维护页，避免写入数据库与上传文件。成功后管理员能查看新版本和可追溯的结果摘要。

## 安全与可操作性验收

- 普通业务管理员与抽样员访问升级 URL、上传和确认接口均被拒绝；系统维护账号错误密码也不能确认。
- 被篡改、无签名、错误公钥、错误平台、重复/过旧版本、Zip Slip、符号链接、压缩炸弹及超限包在切换前拒绝；web 进程不能执行包内容或写入 live release。
- 模拟依赖安装、迁移、健康检查失败时，旧版本保持可用或进入明确的 `recovery_required`；备份及日志可定位。
- 在真实 Ubuntu 测试机上完成一次成功升级和一次故障恢复演练，并核实数据、上传文件、静态资源、移动端与管理端。
- 自签名 HTTPS 仅用于当前临时公网 IP 部署，不改变浏览器证书警告及手机定位的真机验收要求。
